# 为什么不用向量库 / RAG

> 这个仓库最常被问的问题。答案不是"RAG 不好"，而是**它解决的不是这个问题**。

## 两种记忆，一种工具不够

| | 精确事实 | 模糊回忆 |
|---|---|---|
| 例子 | 「Ollama 在 11434 端口」「模型装在 D 盘」「这个项目叫 YG」 | 「上次那个图片处理的坑是怎么踩的来着」 |
| 数据量 | 几十到几百条，每条一行 | 可能几千段 |
| 正确做法 | **全读**，100% 命中 | 检索，命中率 60% 就够用 |
| 用 RAG 会怎样 | 相似度排第 4 条 → 模型看不见 → 它开始编 | 合适 |

**记忆库里 80% 的长命事实都是第一类。** 用相似度检索去取一条"必须精确命中"的事实，是把确定性问题变成概率问题 —— 而这个概率还不是 100%。

## 具体失败模式

| 场景 | 文件方案 | 向量库方案 |
|---|---|---|
| 问「端口是多少」 | `grep 端口 MEMORY.md` → 100% | top-k=5 里没有那条 → 模型编一个 8080 |
| 问「上次那个谁」 | 全读 90 行，命中 | 名字相似度低，排不进前 5 |
| 事实被后来的记录覆盖 | 合并时人工看见冲突，删旧的 | 两条都在库里，检索时可能取到旧的那条 |
| 新机器上部署 | `git clone` → 能用 | 装 embedding 服务 + 建索引 + 版本对齐 |
| 断网 / 离线 | 无所谓，纯文本 | embedding 模型在本地还行，在云上就废 |
| 三个月后回看 | `cat MEMORY.md`，人眼能读 | 打开一个数据库客户端 |

## 成本对比（这个仓库的真实数字）

| 指标 | 本仓库 | 典型 RAG 方案 |
|---|---|---|
| 延迟 | 0.3 秒（读 4 个文件） | 100–800 ms（embedding + 检索） |
| 依赖 | bash/PowerShell + 一个本地小模型（仅整理时用） | 向量库 + embedding 模型 + 通常还要一个 API |
| 磁盘 | 42 KB | 几十 MB 起（含索引） |
| 调试 | `cat` 就完了 | 得看检索日志才知道为什么没召回 |
| 迁移 | 拷贝目录 | 重灌索引 |

## RAG 什么时候对

- 语料是**文档**（说明书、法规、聊天记录全量），不是**事实条目**
- 问题是开放式的（「这份合同里关于违约责任的条款有哪些」）
- 数据量让"全读"不可行（> 200 KB 常驻上下文）
- 允许"召回不全"，答案本身就是综合性的

**这个仓库不管这些。** 它管的是"agent 下一轮开工必须知道的那 90 行"。

## 两者可以共存

```
                     ┌─ 90 行精确事实 ──→ MEMORY.md（全读，这个仓库）
agent 的开工上下文 ──┤
                     └─ 大语料检索 ─────→ 向量库 / RAG（按需）
```

真实系统里两个都该有。**错误在于把后者的工具拿去解前者的题** —— 那才会出现"记忆库明明有这条，它就是答错了"。

## 一句话总结

> 向量库解决的是**「太多读不完」**，不是**「记不住」**。
> 90 行的事实库，读完比搜完快，而且读到的一定是对的那一条。
